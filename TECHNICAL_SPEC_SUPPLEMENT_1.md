## Раздел A. SLA источников данных

### A.1. Назначение

Система OPEN FNR не может формировать расчётный цикл без определённых сроков готовности входных данных. Отсутствие SLA источников означает отсутствие базы для договорённостей с поставщиками данных, нарушение которых невозможно ни зафиксировать, ни эскалировать.

### A.2. Определения

| Термин | Определение |
| --- | --- |
| **Data SLA** | максимально допустимое время появления данных за день D в системе OPEN FNR, после которого фиксируется нарушение |
| **Cutoff time** | момент времени, после которого расчётный пайплайн стартует независимо от полноты входных данных (деградированный режим) |
| **Completeness threshold** | минимальная доля активных магазинов/записей, при которой данные считаются достаточными для старта расчёта |
| **Graceful degradation** | поведение системы при нарушении SLA источника: расчёт по последним доступным данным с алертингом |

### A.3. Целевые SLA по источникам

Приведённые значения являются **стартовыми требованиями к согласованию с владельцами источников**. Итоговые значения фиксируются в Data SLA Agreement с каждым источником.

| Источник | Данные | Целевой SLA (D+1) | Cutoff time | Completeness threshold | Деградация при нарушении |
| --- | --- | --- | --- | --- | --- |
| POS / кассовая система | Продажи за день D | `D+1 06:00` | `D+1 07:00` | ≥ 95% активных магазинов | Расчёт по D-1 продажам с флагом `data_gap` |
| WMS / система управления складом | Остатки магазинов на конец дня D | `D+1 07:00` | `D+1 08:00` | ≥ 90% активных локаций | Расчёт по D-1 остаткам с флагом `stale_stock` |
| WMS | Открытые заказы на дату D | `D+1 07:00` | `D+1 08:00` | ≥ 85% заказов | Использование данных последнего успешного батча |
| WMS | In-transit на дату D | `D+1 07:00` | `D+1 08:00` | ≥ 80% поставок | Использование данных последнего успешного батча |
| ERP | Цены и скидки (действующие на день расчёта) | `D+0 21:00` | `D+0 23:00` | 100% активных SKU с ценой | Использование последних известных цен |
| ERP | Статусы выполнения заказов | `D+1 07:30` | `D+1 08:30` | ≥ 90% открытых заказов | Использование данных предыдущего батча |
| Промо-система | Промо-план на ближайшие 90 дней | Еженедельно, не позднее **воскресенья 20:00** | Воскресенье 22:00 | ≥ 99% промо, стартующих в ближайшие 14 дней | Алерт категорийному менеджеру; расчёт по последнему версионированному плану |
| MDM | Справочник товаров | При изменениях, не позднее `D+0 20:00` | `D+0 23:00` | 100% активных SKU | Использование последней успешной версии MDM с алертом |
| MDM | Справочник магазинов | При изменениях, не позднее `D+0 20:00` | `D+0 23:00` | 100% активных магазинов | Использование последней успешной версии MDM с алертом |
| Внешние факторы (погода, события) | Прогноз на 14 дней | `D+0 22:00` | `D+1 00:00` | — | Расчёт без внешних факторов; fallback признак `no_external_features` |

### A.4. Правила поведения при нарушении SLA

```text
Нарушение SLA источника:
1. Автоматический алерт в канал мониторинга и владельцу источника.
2. Ожидание данных до Cutoff time.
3. При достижении Cutoff time и отсутствии данных — фиксация в audit_log, старт пайплайна
   в режиме graceful degradation.
4. Прогноз, рассчитанный в degraded mode, маркируется флагом quality_flag = 'degraded'.
5. Публикация в автозаказ и ERP — только при явном подтверждении оператором
   или если degraded_publish_allowed = true в конфигурации.
6. Инцидент фиксируется в системе мониторинга со счётчиком SLA нарушений.
```

### A.5. Метрики SLA источников

| Метрика | Целевой уровень | Измерение |
| --- | --- | --- |
| Доля дней с нарушением SLA по POS | ≤ 1% рабочих дней | ежемесячно |
| Среднее отставание продаж от cutoff | ≤ 30 минут | ежедневно |
| Количество расчётов в degraded mode | ≤ 2 в месяц | ежемесячно |
| Доля SKU с устаревшей ценой при расчёте | ≤ 0.1% | ежедневно |

### A.6. Ответственность

Владелец каждого источника данных подписывает **Data SLA Agreement** до начала продуктивной эксплуатации. Неподписанный SLA Agreement является блокером для перехода в production.

## Раздел B. Lifecycle ML-моделей и Governance

### B.1. Назначение

Описывает весь жизненный цикл модели от эксперимента до production и обратно, включая триггеры переобучения, champion/challenger протокол, fallback-цепочку и критерии аварийного отзыва.

### B.2. Стадии жизненного цикла модели

```text
EXPERIMENT → CANDIDATE → SHADOW → CHAMPION → RETIRED
                                       ↑
                            CHALLENGER (параллельно)
```

| Стадия | Описание | Хранение в MLflow |
| --- | --- | --- |
| `EXPERIMENT` | Разработка DS-командой, нет SLA | тег `stage=experiment` |
| `CANDIDATE` | Прошёл backtesting, готов к shadow | тег `stage=candidate` |
| `SHADOW` | Считает параллельно champion, результаты не публикуются | тег `stage=shadow` |
| `CHAMPION` | Активная production-модель | тег `stage=champion` |
| `CHALLENGER` | Альтернативная модель в shadow против champion | тег `stage=challenger` |
| `RETIRED` | Выведена из эксплуатации, артефакты сохранены | тег `stage=retired` |

### B.3. Минимальные требования для регистрации CANDIDATE

Модель не может получить статус `CANDIDATE` без выполнения всех условий:

| Требование | Порог |
| --- | --- |
| Backtesting WAPE на hold-out | лучше current champion на ≥ 0.5 п.п. или не хуже champion на ≤ 1 п.п. |
| Backtesting Bias | `|Bias| < 5%` на сводном срезе |
| Минимум недель в backtesting window | ≥ 26 недель (half-year rolling) |
| Покрытие сегментов | fast + medium + slow + promo + fresh — все сегменты протестированы |
| Версия данных зафиксирована | `data_version` записан в MLflow run |
| Параметры зафиксированы | `hyperparameters` записаны в MLflow run |
| Артефакты сохранены | model binary + feature list + preprocessing pipeline |
| Код воспроизводим | git commit hash записан в MLflow run |

### B.4. Shadow Deployment Protocol

1. CANDIDATE переводится в `SHADOW` на **минимум 14 календарных дней**.
2. В shadow-режиме модель получает те же входные данные, что и champion, и пишет прогнозы в отдельную таблицу `forecast_shadow`.
3. Ежедневно рассчитывается сравнительный WAPE: `shadow_wape` vs `champion_wape`.
4. По завершении shadow-периода DS-лид формирует **Shadow Report** (HTML, в `docs/model-reports/`).
5. **Критерии для продвижения** из shadow в champion:

| Условие | Требование |
| --- | --- |
| Shadow WAPE | не хуже champion на > 1 п.п. (на сводном срезе) |
| Bias в shadow | `|Bias| < 5%` |
| Аномальные прогнозы | доля прогнозов с отклонением > 5σ не выше, чем у champion |
| Инцидентов в shadow | 0 критических (прогноз не рассчитан, crash) |

### B.5. Триггеры переобучения (Retraining Triggers)

Переобучение запускается **автоматически** при наступлении любого из условий:

| Триггер | Порог | Действие |
| --- | --- | --- |
| WAPE drift (скользящий 7-дневный avg vs baseline 28 дней) | деградация > 3 п.п. | Автоматический запуск retraining pipeline |
| Population Stability Index (PSI) входных признаков | PSI > 0.2 хотя бы для одного из top-10 признаков | Запуск retraining + алерт DS-команде |
| Data drift (KS-test p-value) для целевой переменной | p < 0.05 за 7 дней подряд | Запуск retraining + алерт |
| Доля fallback прогнозов (не рассчитаны основной моделью) | > 5% активных связок | Алерт DS + ручной триггер retraining |
| Плановый retraining | Еженедельно (по расписанию, воскресенье) | Автоматически |
| Ручной триггер | DS-лид через API/UI | Немедленно |

Переобучение **не** запускает автоматическую смену champion. Новая модель проходит полный цикл CANDIDATE → SHADOW → Champion.

### B.6. Fallback Chain

При отказе или деградации champion-модели применяется следующая цепочка:

```text
Level 1: Champion model (production)
    ↓ (WAPE drift > 5 п.п. или model crash)
Level 2: Предыдущий champion (N-1 версия, сохранена в MLflow)
    ↓ (N-1 тоже недоступна или degraded)
Level 3: Category-level median forecast (скользящий median по категории за 28 дней)
    ↓ (данные для категории отсутствуют)
Level 4: Store-level rolling median (28-дневный rolling median по магазину)
    ↓ (данные по магазину отсутствуют)
Level 5: Global seasonal naive (продажи аналогичного дня недели год назад)
```

Каждый прогноз маркируется `model_tier` = 1..5 и `quality_flag`.  
Публикация в автозаказ при `model_tier` ≥ 4 требует явного подтверждения оператора.

### B.7. Критерии аварийного отзыва модели (Emergency Rollback)

Champion-модель немедленно откатывается на N-1 версию при:

| Условие | Порог |
| --- | --- |
| Сводный WAPE за последние 3 дня | хуже N-1 champion на > 5 п.п. |
| Доля нулевых или отрицательных прогнозов | > 2% активных связок |
| Прогнозы с абсолютным отклонением > 10x от исторической медианы | > 0.5% активных связок |
| Критический баг, подтверждённый DS-лидом | любой |

Rollback выполняется в течение **1 часа** после обнаружения условия.

### B.8. Документационные артефакты модели

Каждая модель в стадии CHAMPION должна иметь:

- Model Card (назначение, входные данные, метрики, ограничения, known biases).
- Shadow Report (результаты сравнения с предыдущим champion).
- Training Data Report (объём, период, распределение по сегментам).
- Ссылку на git commit с кодом обучения.

## Раздел C. Финансовые параметры оптимизации пополнения

### C.1. Назначение

Формулы расчёта заказов в TECHNICAL_SPEC.md (раздел 22.7) содержат целевую функцию:

```text
total_cost = lost_sales_cost + waste_cost + holding_cost + order_cost
```

Без согласованных стоимостных параметров эта формула неисполняема. Настоящий раздел определяет структуру параметров, методику их получения и обязательность согласования с бизнесом до старта production-расчёта.

### C.2. Параметры оптимизации — структура

#### C.2.1. Holding Cost (Стоимость хранения)

| Параметр | Описание | Единица | Стартовое значение | Источник |
| --- | --- | --- | --- | --- |
| `holding_cost_rate_annual` | Годовая ставка стоимости хранения (финансовый подход: стоимость капитала + складские расходы) | % от стоимости запаса в год | **согласуется с финансовым директором** | Финансовая модель компании |
| `holding_cost_per_unit_per_day` | Альтернативный операционный параметр: стоимость хранения единицы SKU в день в магазине | руб./шт./день | рассчитывается по `holding_cost_rate_annual` | — |

Типовой диапазон `holding_cost_rate_annual` для FMCG-ритейла: **18–30% в год**. Итоговое значение **подписывается финансовым директором** и является обязательным входом системы.

Для fresh-категорий holding cost включает дополнительную компоненту — стоимость риска порчи:

```text
fresh_holding_cost = base_holding_cost + spoilage_risk_cost
```

#### C.2.2. Lost Sales Cost (Стоимость упущенной продажи)

| Параметр | Описание | Единица | Обязательность |
| --- | --- | --- | --- |
| `lost_sales_margin_rate` | Доля маржи, которую компания теряет при одной упущенной единице продажи | % от отпускной цены | Обязателен |
| `lost_sales_loyalty_multiplier` | Множитель для loyal customer SKU (потеря лояльного покупателя дороже разовой продажи) | безразмерный, ≥ 1.0 | По решению бизнеса |
| `lost_sales_category_override` | Переопределение ставки по категории (например, табак — регуляторный аспект, хлеб — социальный) | % от цены | По категориям |

**Обязательные ставки** согласуются с коммерческим директором до пилота. До согласования используется единая ставка `lost_sales_margin_rate = gross_margin_rate` SKU.

#### C.2.3. Waste Cost (Стоимость списания)

| Параметр | Описание | Единица |
| --- | --- | --- |
| `waste_cost_per_unit` | Себестоимость списанной единицы + утилизация | руб./шт. |
| `waste_cost_rate` | Альтернатива: доля закупочной цены | % от закупочной цены |

Для расчёта достаточно одного параметра (`waste_cost_per_unit` или `waste_cost_rate`). Выбор метода фиксируется в конфигурации категории.

#### C.2.4. Service Level Targets (Целевые уровни сервиса)

Уровень сервиса определяет допустимую вероятность stock-out и является **ключевым входом для расчёта safety stock**.

| Сегмент | Целевой Service Level | Пример категорий |
| --- | --- | --- |
| A (высокооборотные, критичные) | ≥ **98%** | хлеб, молоко, вода, базовые SKU |
| B (стандартные) | ≥ **95%** | большинство FMCG |
| C (нишевые, длинный хвост) | ≥ **90%** | узкий ассортимент |
| Fresh ультра (срок годности ≤ 3 дней) | ≥ **96%** (с балансом waste) | хлеб собственного производства |
| Seasonal (сезонные остатки) | ≥ **92%** в сезон, clearance вне сезона | — |
| Slow movers | ≥ **85%** | — |
| Промо SKU в период акции | ≥ **98%** | — |

Значения **подписываются коммерческим директором** и директором по цепочке поставок до начала production-расчёта. Они загружаются как конфигурационные параметры в БД, изменяются через UI с audit trail.

### C.3. Методология расчёта Safety Stock

Система поддерживает **три уровня методов** расчёта safety stock в зависимости от доступных данных:

| Метод | Применимость | Формула |
| --- | --- | --- |
| **Normal distribution** (базовый) | Стабильный спрос, CV < 0.5 | `SS = z(SL) × σ_demand × √LT` |
| **DDLT (Demand During Lead Time)** | Вариативный lead time | `SS = z(SL) × √(LT × σ²_demand + demand² × σ²_LT)` |
| **Empirical quantile** | Slow movers, intermittent demand, нет нормального распределения | `SS = quantile(SL, historical DDLT distribution)` |

Выбор метода определяется автоматически по CV (Coefficient of Variation) и частоте продаж SKU.

Параметры по умолчанию:

| Параметр | Значение по умолчанию | Переопределяется |
| --- | --- | --- |
| Review period | 1 день (ежедневный расчёт) | по типу локации |
| Lead time variability | σ_LT по истории поставщика | из данных WMS |
| Demand variability | σ_demand: rolling std за 28 дней | пересчитывается еженедельно |

### C.4. ABC/XYZ Сегментация — методология

Сегментация является **обязательным входом** для выбора модели прогнозирования и метода safety stock.

#### C.4.1. ABC по обороту (за скользящие 13 недель)

| Сегмент | Критерий | Доля SKU (ориентир) |
| --- | --- | --- |
| A | Накопленный оборот до 80% | ~15-20% SKU |
| B | Следующие 15% оборота (80–95%) | ~25-30% SKU |
| C | Оставшиеся 5% оборота (95–100%) | ~50-60% SKU |

Оборот считается на уровне **сети** (не магазина). Для категорийного менеджера доступна переопределение сегмента на уровне категории.

#### C.4.2. XYZ по стабильности (за скользящие 13 недель)

| Сегмент | Критерий (CV = σ/μ продаж за неделю) |
| --- | --- |
| X | CV ≤ 0.3 (стабильный спрос) |
| Y | 0.3 < CV ≤ 0.6 (умеренная вариативность) |
| Z | CV > 0.6 (нестабильный, сезонный, intermittent) |

SKU без достаточной истории (< 6 недель продаж) получают сегмент `NEW`.

#### C.4.3. Матрица применения

| Сегмент | Модель прогноза | Метод SS | Service Level |
| --- | --- | --- | --- |
| AX | LightGBM/CatBoost | Normal distribution | 98% |
| AY | LightGBM/CatBoost | DDLT | 97% |
| AZ | LightGBM/CatBoost + seasonal | Empirical quantile | 97% |
| BX | LightGBM/CatBoost | Normal distribution | 95% |
| BY | LightGBM/CatBoost | DDLT | 95% |
| BZ | Category model | Empirical quantile | 93% |
| CX | Rolling median / Category model | Normal distribution | 90% |
| CY | Rolling median | Empirical quantile | 90% |
| CZ | Baseline / Naive | Empirical quantile | 88% |
| NEW | Cold start (reference products) | Empirical quantile категории | согласно категории |

#### C.4.4. Пересчёт сегментов

Сегменты пересчитываются еженедельно (воскресенье). Смена сегмента логируется в audit. При смене модельной группы (например, C → B) новая модель применяется с понедельника следующей недели.

## Раздел D. Параллельный запуск и бизнес-приёмка

### D.1. Назначение

Определяет формальный процесс перехода от прототипа/пилота к production, включая период параллельного запуска, числовые критерии приёмки и процедуру sign-off.

### D.2. Фазы перехода

```text
SHADOW MODE → PARALLEL RUN → CONTROLLED PILOT → FULL PRODUCTION
```

#### D.2.1. Shadow Mode (≥ 4 недели)

- Система рассчитывает прогнозы и заказы параллельно с текущим процессом.
- **Никакие экспорты в ERP/WMS не производятся.**
- DS/DE-команда ежедневно сравнивает OPEN FNR прогнозы с фактическими продажами.
- Готовится Shadow Mode Report.

#### D.2.2. Parallel Run (≥ 6 недель, включая минимум 1 промо-цикл)

- Система формирует предложения заказов.
- Экспорт производится для **тестовой группы магазинов** (см. D.3).
- В магазинах контрольной группы продолжает работать текущий процесс.
- Еженедельный сравнительный KPI-отчёт.

#### D.2.3. Controlled Pilot

- Полный набор функций включён для пилотных магазинов.
- Длительность: согласовывается с бизнесом, но **минимум 8 недель**.
- Критерии выхода: см. D.4.

#### D.2.4. Full Production

- Включение оставшихся магазинов по план-графику.
- График rollout согласуется с IT и операционным директором.

### D.3. Контрольная группа — методология

Для достоверного измерения бизнес-эффекта используется **matched pair** подход:

1. Из сети выбираются пары магазинов с максимальной схожестью по:
   - формату магазина;
   - среднему обороту;
   - региону;
   - составу категорий (доля fresh, промо-активность).
2. В каждой паре один магазин — **тест** (OPEN FNR), второй — **контроль** (текущий процесс).
3. Минимальное число пар: **30** для статистической значимости.
4. Пары фиксируются до старта эксперимента и не меняются в течение Parallel Run.

Без контрольной группы бизнес-эффект не может быть подтверждён. Наличие контрольной группы является **обязательным условием** для sign-off пилота.

### D.4. Числовые критерии бизнес-приёмки

Все пороги **согласуются с коммерческим директором и директором по цепочке поставок** и фиксируются до старта Parallel Run.

#### D.4.1. Метрики точности прогноза

| Метрика | Тестовая группа | Контрольная группа | Критерий приёмки |
| --- | --- | --- | --- |
| WAPE (all categories) | измеряется | измеряется | OPEN FNR WAPE **< контроль** на ≥ 2 п.п. |
| WAPE (fresh) | измеряется | измеряется | OPEN FNR WAPE **< контроль** на ≥ 1.5 п.п. |
| WAPE (promo weeks) | измеряется | измеряется | OPEN FNR WAPE **< контроль** на ≥ 3 п.п. |
| Bias | измеряется | — | `|Bias| < 3%` для сводного среза |

Конкретные числовые пороги (2 п.п., 1.5 п.п., 3 п.п.) являются **стартовыми предложениями** и заменяются согласованными значениями до старта пилота.

#### D.4.2. Операционные KPI

| KPI | Измерение | Минимальный уровень для приёмки |
| --- | --- | --- |
| Out-of-stock rate (доля SKU-дней без товара) | тест vs контроль | Снижение на ≥ 15% в тестовой группе |
| Overstock value (рублей избыточного запаса) | тест vs контроль | Снижение на ≥ 10% |
| Fresh waste (% от оборота fresh) | тест vs контроль | Снижение на ≥ 10% |
| Proposal acceptance rate (доля принятых предложений без изменений) | только тест | ≥ 80% после 4 недель работы |
| Manual adjustment rate | только тест | Снижение к концу пилота ≥ 20% к baseline |

#### D.4.3. Технические критерии

| Критерий | Требование |
| --- | --- |
| Расчётный SLA | ≥ 95% дней расчёт завершается в установленный SLA |
| Критические инциденты (p1) | 0 за последние 2 недели Parallel Run |
| Деградированный режим | ≤ 2 раза за весь Parallel Run |
| UAT sign-off от ключевых пользователей | ≥ 80% ключевых ролей подписали UAT |

### D.5. Sign-off матрица

| Стейкхолдер | Что подписывает | Обязательность |
| --- | --- | --- |
| Коммерческий директор | Метрики точности прогноза + OOS KPI | Обязателен |
| Директор по SC/автозаказу | Операционные KPI + технические критерии | Обязателен |
| IT-директор | Технические критерии + безопасность | Обязателен |
| Категорийный менеджер (минимум 3 категории) | UAT по рабочим местам | Обязателен |
| Финансовый директор | Экономический эффект (P&L impact) | Обязателен |
| DS-лид | Модельные метрики + Shadow Report | Обязателен |

Без полного комплекта подписей переход в Full Production **блокируется**.

## Раздел E. Disaster Recovery и Business Continuity

### E.1. Требования к RPO и RTO

| Компонент | RPO (максимальная потеря данных) | RTO (время восстановления) |
| --- | --- | --- |
| Forecast Store (ClickHouse) | 1 час | 2 часа |
| Metadata DB (PostgreSQL) | 15 минут | 1 час |
| Audit Log | 0 (synchronous replication) | 30 минут |
| ML Model Registry (MLflow) | 24 часа | 4 часа |
| Конфигурации и бизнес-правила | 1 час | 2 часа |
| Последний успешный прогноз | 0 (hot standby) | 15 минут |

### E.2. Стратегия резервного копирования

| Данные | Частота | Хранение | Метод |
| --- | --- | --- | --- |
| PostgreSQL (metadata, audit) | Каждые 15 минут (WAL shipping) + полный ежедневно | 30 дней | pg_basebackup + WAL archiving |
| ClickHouse (forecast, order proposals) | Ежедневно | 14 дней | clickhouse-backup |
| Raw/Clean данные (Iceberg/Parquet) | Инкрементально при записи | 3 года | Object storage replication |
| ML model artifacts (MLflow) | При каждой регистрации версии | Без ограничения (только retired models — 3 года) | Object storage |
| Process definitions (BPMN/DMN/CMMN) | При каждом деплое | Без ограничения | Git + object storage |
| Конфигурации системы | При каждом изменении | 1 год | Git |

### E.3. Сценарии аварий и планы восстановления

| Сценарий | Влияние | Действие | RTO |
| --- | --- | --- | --- |
| Отказ ClickHouse single node | Нет доступа к прогнозам и BI | Переключение на replica / restore из backup | 2 часа |
| Отказ PostgreSQL | Нет API, нет audit | Failover на standby (автоматически) | 15 минут |
| Отказ пайплайна Airflow | Прогноз не рассчитан в срок | Ручной запуск trigger-DAG, публикация предыдущей версии | 1 час |
| Потеря champion-модели | Нет inference | Восстановление из MLflow artifact storage, fallback на N-1 | 30 минут |
| Недоступность всех источников данных | Полный degraded mode | Публикация последнего успешного прогноза с флагом | 30 минут |
| Компрометация секретов | Риск несанкционированного доступа | Ротация всех секретов, аудит доступа, уведомление IR-команды | 1 час |

### E.4. Ежеквартальное DR-тестирование

- Раз в квартал проводится **плановое DR-учение** в STAGE-среде.
- Тестируются сценарии: отказ ClickHouse, отказ PostgreSQL, потеря модели.
- Результаты фиксируются в DR Test Report.
- Реальный RTO из DR-теста сравнивается с целевым. Отклонение > 50% — обязательная доработка.

## Раздел G. API Versioning и Deprecation Policy

### G.1. Versioning Schema

Все публичные API OPEN FNR версионируются через URL-prefix:

```text
/api/v{major}/
```

Пример: `/api/v1/forecast`, `/api/v2/replenishment/proposals`.

Правила смены версий:

| Тип изменения | Действие |
| --- | --- |
| Добавление нового поля в ответ | Без смены версии (backward compatible) |
| Добавление нового endpoint | Без смены версии |
| Изменение типа поля, удаление поля | Новая major версия |
| Изменение семантики существующего поля | Новая major версия |
| Изменение структуры ошибок | Новая major версия |

### G.2. Deprecation Policy

| Этап | Требование |
| --- | --- |
| Объявление deprecation | Минимум за **90 дней** до отключения старой версии |
| Уведомление потребителей | Email + changelog + заголовок `Deprecation: YYYY-MM-DD` в ответах API |
| Параллельная поддержка | Старая и новая версии работают **одновременно** минимум 90 дней |
| Sunset | Отключение только при подтверждении от всех зарегистрированных потребителей |
| Emergency deprecation | При критическом security issue — 7 дней с уведомлением |

### G.3. Реестр потребителей API

Каждый внешний потребитель API (автозаказ, ERP, BI, WMS) регистрируется:

- Название системы и команды.
- Используемые endpoints.
- Контактное лицо для уведомлений.
- Версия API.

Реестр ведётся в `docs/api-consumers/registry.md`. Обновление реестра — ответственность API-владельца.

### G.4. Стандарт ошибок API

Все ошибки API возвращают унифицированную структуру:

```json
{
  "error_code": "FORECAST_NOT_FOUND",
  "message": "Forecast for store_id=1001, run_date=2026-06-01 not found",
  "request_id": "uuid",
  "timestamp": "2026-06-01T08:00:00Z",
```

| Класс | Описание | Примеры | Требования к защите |
| --- | --- | --- | --- |
| **C1 — Public** | Данные, доступные всем авторизованным пользователям системы | Агрегированный прогноз по сети, статусы расчёта | Аутентификация |
| **C2 — Internal** | Операционные данные, ограниченные ролями | Прогнозы по магазинам, order proposals, KPI | RBAC по роли + региону/категории |
| **C3 — Confidential** | Коммерчески чувствительные данные | Цены, условия поставщиков, MOQ/MOV, промо-план | RBAC + row-level security + audit log доступа |

### H.2. Supplier Data Isolation

Поставщик, получающий доступ к Supplier Collaboration модулю, должен видеть **только данные, относящиеся к его SKU и его поставкам**.

Требования к изоляции:

| Требование | Описание |
| --- | --- |
| Row-level isolation | Поставщик X не может получить данные поставщика Y через API |
| Forecast visibility | Поставщик видит только агрегированный forecast/order forecast по своим SKU; детализация по магазинам — по согласованию |
| Performance data | Поставщик видит только свои fill rate и on-time delivery metrics |
| No cross-supplier inference | Нельзя вычислить данные конкурента через разницу агрегатов |
| Authentication | Каждый поставщик имеет отдельный service account с ограниченными scopes |
| Audit | Каждый запрос поставщика логируется |

Технически изоляция реализуется через:

1. Supplier scope в JWT-токене (`supplier_id` claim).
2. Row-level security в API (фильтрация по `supplier_id` до возврата данных).
3. Отдельные API endpoints для supplier-facing интеграций (`/supplier-api/v1/`).

## Раздел I. Intraday и Demand Sensing — Scope-решение

### I.1. Scope для версии v1 (пилот и production)

**Intraday расчёт прогноза и пополнения НЕ входит в v1.**

Обоснование:
- v1 строится на batch-архитектуре с ежедневным ночным расчётом.
- Intraday требует streaming ingestion (Kafka/Redpanda), near-realtime feature store и online inference — отдельный архитектурный контур.
- Источники данных (POS, WMS) в v1 предоставляют батчи, а не потоковые события.

### I.2. Компенсирующие меры для fresh в v1

Несмотря на отсутствие intraday расчёта, для fresh-категорий применяются:

| Мера | Описание |
| --- | --- |
| Более ранний cutoff | Fresh batch отдельный; данные свежее (POS fresh-поставки доступны к 05:00) |
| Intraday alert (не forecast) | Если к 12:00 остаток fresh SKU < 20% от opening stock — alert в Store Management без пересчёта прогноза |
| Ежедневный пересчёт утром | Fresh-расчёт запускается раньше основного batch (приоритетная партиция) |

### I.3. Roadmap для v2

Intraday/demand sensing запланирован в **v2** и потребует:

- Streaming ingestion (Kafka или Redpanda, Apache-2.0).
- Online feature store (отдельный контур).
- Intraday replenishment trigger для fresh (не прогноз, а коррекция заказа).
- Рассматривается для dark store и e-commerce fulfillment center в первую очередь.

## Раздел J. Historical Replenishment Simulation

### J.1. Назначение

До старта Parallel Run система должна пройти **Historical Simulation** — ретроспективный расчёт заказов на исторических данных за ≥ 52 недели.

Цель: доказать, что replenishment engine при данных прошлого года формировал бы заказы, улучшающие service level и снижающие waste/overstock.

### J.2. Требования к Historical Simulation

| Требование | Значение |
| --- | --- |
| Период симуляции | Последние 52 недели (включая минимум 2 промо-волны и 1 сезонный цикл) |
| Объём | Не менее 20% активных магазинов и 50% категорий по обороту |
| Метод | Rolling simulation: каждую неделю — перерасчёт заказов с использованием данных, доступных на тот момент |
| Сравнение | OPEN FNR заказы vs фактические заказы (текущий процесс) |

### J.3. Метрики Historical Simulation

| Метрика | Как считается |
| --- | --- |
| Simulated OOS rate | Если projected stock после применения OPEN FNR заказа < 0 до следующей поставки |
| Simulated overstock | Projected stock > max_stock target |
| Simulated waste (fresh) | Projected remaining stock > 0 на дату окончания срока годности |
| Proposal vs actual delta | Среднее абсолютное отклонение предложенного заказа от фактического |

### J.4. Результат

Historical Simulation Report (HTML, в `docs/simulation-reports/`) является **обязательным входом** для решения о старте Parallel Run. Без позитивного результата симуляции Parallel Run не стартует.

## Раздел L. OTB / Seasonal Budget Integration

### L.1. Scope-решение для v1

**Интеграция с Open-to-Buy (OTB) / бюджетной системой НЕ входит в v1.**

В v1 система формирует order proposals без финансовых ограничений сверху. Планировщик или категорийный менеджер применяет бюджетные ограничения вручную через массовую корректировку.

### L.2. Требования для v2

В v2 предусматривается:

| Функция | Описание |
| --- | --- |
| OTB constraint input | Загрузка недельного/месячного бюджета закупок по категориям через API или файл |
| Budget-aware order shaping | Replenishment engine учитывает OTB-лимит при расчёте предложений заказов; приоритет отдаётся A-сегменту |
| Budget utilization view | BI-страница: план vs факт по OTB в разрезе категорий и поставщиков |
| Seasonal buy integration | Pre-season закупка формируется как отдельный тип расчёта с горизонтом до конца сезона и с OTB-ограничением |
| Markdown recommendation | При end-of-season overhang система предлагает уценки (интеграция с системой ценообразования или экспорт рекомендаций) |

### L.3. Компенсирующая мера для v1 (сезонное планирование)

До реализации OTB-интеграции:

- Seasonal planning horizon в v1 — до 90 дней.
- Для сезонных SKU применяется ограничение `max_stock = N * selling_days` через параметр в MDM.
- End-of-season clearance управляется через `termination_date` и lifecycle workflow.
- **Ответственность** за соблюдение бюджетного лимита — у категорийного менеджера в UI.
