OPEN FNR / Sprint 2 / Data Quality Console

Отчёт по UI-тестированию и тестированию бизнес-процессов

Отчёт фиксирует тестовый цикл Sprint 2: видимость качества данных, блокирующие инциденты, waiver-контроль и процессную логику DQ.

Аннотация теста

Мы тестируем Data Quality Console и связанные BPMN/DMN/CMMN артефакты, потому что качество входных данных напрямую определяет возможность публиковать прогноз и передавать результаты в пополнение. Метод выбран комбинированный: API-тесты проверяют контракт, процессные тесты проверяют исполнимые артефакты, UI-сборка и скриншот подтверждают, что пользователь видит состояние DQ без ручного анализа логов.

UI-тестирование

Шаг Что делаем Зачем Почему именно так Ожидаемый результат Фактический результат
1 Открываем главную страницу Dev Control Tower. Проверить, что пользователь попадает в рабочий экран, а не в пустую страницу. Smoke-навигация ловит самые ранние поломки UI. Отображаются модули Forecasting, Replenishment, Process. Отображаются.
2 Проверяем блок Data Load Status. Убедиться, что пользователь видит состояние загрузок по доменам. Sprint 2 зависит от Sprint 1, поэтому DQ должен быть связан с batch status. Видны Sales, Stock, Prices, Product MDM, Store MDM. Видны.
3 Проверяем Data Quality Console. Показать блокирующие и предупреждающие DQ-инциденты. Планировщику и Data Owner нужен единый экран для принятия решения. Видны severity, incident id, affected rows, owner и message. Видны.
4 Проверяем действия Re-run, Waive, Export rows. Подтвердить наличие ожидаемых пользовательских команд. Пока действия статичны, но UI-контракт уже закрепляет будущую интеграцию. Кнопки доступны в карточке выбранного инцидента. Доступны.

Тестирование бизнес-процессов

Процесс Шаг Что делаем Зачем Ожидаемый результат Фактический результат
dq_check_process 1 Стартуем процесс после готовности clean batch. Проверить входную точку DQ перед публикацией данных. BPMN содержит start event и service task Run DQ rules. Подтверждено XML-тестом.
dq_check_process 2 Проверяем ветвление по blockingIncidentCount. Блокирующие ошибки не должны проходить в публикацию. Есть gateway и ветка Review blocking DQ incident. Подтверждено XML-тестом.
dq_check_process 3 Проверяем re-run после ручного review. После исправления данных нужно повторно подтвердить качество. Есть service task Re-run DQ rules. Подтверждено XML-тестом.
dq_severity_decision 1 Проверяем DMN-таблицу severity. Severity должна быть правилом, а не hardcode в UI. DMN содержит decisionTable. Подтверждено XML-тестом.
publication_block_decision 1 Проверяем правило блокировки публикации. Прогноз не должен публиковаться при blocker без waiver. DMN содержит правило block_publication. Подтверждено XML-тестом.
data_quality_incident_case 1 Проверяем CMMN case с triage, fix source data и approve waiver. Инциденты DQ требуют совместной работы Data Engineering и Data Owner. CMMN содержит human tasks Triage DQ incident и Approve waiver. Подтверждено XML-тестом.
